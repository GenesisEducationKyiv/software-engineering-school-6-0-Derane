# github-release-notifier - Epic Breakdown

## Overview

This document provides the complete epic and story breakdown for the **REST → gRPC migration**,
decomposing the PRD and Architecture of `specs/rest-to-grpc-migration/` into implementable stories. The
assignment replaces **one synchronous inter-service call** with a gRPC unary RPC. The load-bearing
reality (PRD §1, onboarding §2) is that **no synchronous service-to-service REST call exists today** —
all monolith ↔ notification traffic is async RabbitMQ. So this is not a one-for-one swap: we keep the
async `rabbit` path as the **default and the HW9 backstop**, and add two **opt-in synchronous twins**
(`rest`, `grpc`) over the *same unchanged* `SendWelcomeEmailHandler` (Service B), selected by
`WELCOME_EMAIL_TRANSPORT` (default `rabbit`). Service A (the monolith saga relay) calls Service B and
blocks for the `sent|failed` outcome (the deliberate caller-waits semantic shift, DC1).

The new code is **all Infrastructure on both sides** (D-arch §1): a gRPC server (`WelcomeEmailGrpcService`)
and a REST controller (`WelcomeEmailController`) on Service B over the unchanged handler; two
`WelcomeEmailRelay`-shaped client adapters (`GrpcWelcomeEmailRelay`, `RestWelcomeEmailRelay`) behind a new
sibling outcome-returning port (`SyncWelcomeEmailSender`, D5) on Service A. The gRPC contract is a **new**
`proto/notification/welcome/v1/welcome.proto` (package `notification.welcome.v1`, D3), generated by **buf**
into an isolated `gen/` tree (D2/NFR4) — the legacy `proto/release_notifier.proto` and committed
`generated/` are frozen (N2/N7/FR12). Errors map through a notification-side `toGrpcStatus()` on the
existing `ExceptionStatusMap` (D7/FR6). Both deptrac baselines stay `{}` (D8/NFR5/R7).

The plan is executed **dependency-ordered along the architecture P0→P9 migration ladder**
(arch §12), in five epics. Every story keeps the quality gates green: monolith `composer lint`
(PHPCS PSR-12 **+ deptrac**), `./vendor/bin/phpunit --no-coverage --testsuite Unit`, `composer psalm`
(100%); stories that touch `apps/notification` also run the service's equivalent gates. The **deptrac
baseline stays `{}`** on both deployables (NFR5) — every new edge reuses an existing Infrastructure layer,
no new layer, no baseline exception. The default `rabbit` path keeps the **HW9 saga + all HW7/HW9 tests +
Behat green throughout** (FR12/NFR1/AC7/AC8).

> Epic-to-phase map: **Epic 1 = P0–P1**, **Epic 2 = P2–P4**, **Epic 3 = P5–P6**,
> **Epic 4 = P7 (+ test stories ride P2–P6)**, **Epic 5 = P8–P9**.

## Requirements Inventory

### Functional Requirements

FR1: **Versioned, documented proto contract with a unary RPC.** A **new**
`proto/notification/welcome/v1/welcome.proto` (file path matches the package dir → buf
`PACKAGE_DIRECTORY_MATCH`) declares `package notification.welcome.v1`,
`option php_namespace = "Notification\\Welcome\\V1"`, and one **unary**
`SendWelcomeEmail(SendWelcomeEmailRequest) returns (SendWelcomeEmailResponse)` whose response carries a
`sent|failed` outcome (`enum Outcome {OUTCOME_UNSPECIFIED=0; OUTCOME_SENT=1; OUTCOME_FAILED=2;}` —
`OUTCOME_`-prefixed for buf `ENUM_VALUE_PREFIX`) + an optional `error_detail`; the request carries
`int64 subscription_id` (RD10a, no truncation). RPC/messages/fields have self-documenting names and doc
comments. The existing `proto/release_notifier.proto` is unchanged (N2).

FR2: **buf wired and clean (greenfield).** `buf.yaml` (v2; `modules: - path: proto`; `lint: STANDARD`;
`breaking: FILE`; legacy proto ignored from lint) **and** `buf.gen.yaml` (three plugins: remote
`buf.build/protocolbuffers/php` messages, local vendored Spiral server interface, remote `buf.build/grpc/php`
client stub) exist; `buf lint` is **fully offline** and reports zero findings, and `buf generate` (which
needs network for the two remote plugins; offline fallback = pinned `grpc_php_plugin` + a `protoc-gen-php`
shim) emits PHP stubs into a **dedicated `gen/` dir separate from `generated/`**, autoloaded under its own
PSR-4 prefix. buf + plugin versions are pinned.

FR3: **Synchronous REST baseline endpoint.** Service B exposes a **new** `POST /internal/welcome-emails`
that accepts a welcome-email send request (`sagaId`, `subscriptionId`, `email`, `repository`), invokes the
**unchanged** `SendWelcomeEmailHandler`, and returns the `sent|failed` outcome as JSON with the matching
HTTP status. It is the benchmark **baseline** and is **kept working** after gRPC lands (never deleted).

FR4: **gRPC unary server over the same handler.** Service B exposes a gRPC unary server
(`WelcomeEmailGrpcService` on RoadRunner) implementing the FR1 service, invoking the **same unchanged**
handler and returning `SendWelcomeEmailResponse{outcome}`. This is a net-new gRPC surface in
`apps/notification` (gRPC deps + RoadRunner entrypoint + DI + a second supervised process).

FR5: **No business-logic change in Service B.** REST and gRPC are **transport adapters only** over the
existing `SendWelcomeEmailHandler`; its claim/render/send/markSent logic, ledger/idempotency, and outcome
computation are unchanged. The notification `Application` layer has no behavioral diff; existing
notification tests stay green.

FR6: **gRPC status-code mapping reuses `ExceptionStatusMap`.** Handler errors map to gRPC status codes via
a notification-side `toGrpcStatus()` built on the existing `ExceptionStatusMap`, honoring the PRD §6
HTTP→gRPC table, used by **both** the REST status (`toHttpStatus()`) and the gRPC status so an exception
maps consistently across transports.

FR7: **Flag-selected client adapters that actually call Service B.** Two new `WelcomeEmailRelay`-shaped
adapters — `RestWelcomeEmailRelay` and `GrpcWelcomeEmailRelay` — implement the new sibling
`SyncWelcomeEmailSender` port, are wired in `config/container.php`, and selected by
`WELCOME_EMAIL_TRANSPORT`. When the flag is `grpc` the relay **actually invokes** Service B's gRPC server
and obtains `sent|failed`; when `rest` it calls the REST endpoint. The existing `RabbitWelcomeEmailRelay`
(`void`, async) remains and is selected by `rabbit`. On the sync paths the caller **waits** for the
outcome (DC1) and then drives the saga by dispatching the existing `HandleWelcomeEmailOutcomeCommand`; the
async `void` contract and the HW9 saga state machine are unchanged.

FR8: **Transport selection by env flag, default `rabbit`.** `WELCOME_EMAIL_TRANSPORT` (`rabbit | rest |
grpc`) selects the relay; an **absent or unrecognized** value defaults to **`rabbit`**. All three are
wired simultaneously; switching the flag switches the path with no code change and **no REST deletion**.

FR9: **Automated test on the gRPC path.** At least one automated test exercises the gRPC path with (a) a
**happy path** asserting `outcome: sent` / `OK`, and (b) **≥1 error case asserting the correct gRPC status
code**, via the established in-process gRPC pattern (`tests/Grpc/` / `tests/Integration/Grpc/`: mocked
`ContextInterface`, real status map). The REST baseline is likewise covered so the comparison is honest.

FR10: **★ k6 REST-vs-gRPC benchmark + README comparison.** A single **k6** harness drives the REST
baseline (HTTP) and the gRPC path (`k6/net/grpc`); the README records req/s and latency p50/p95/p99 for
both and the difference, with a short explanation (HTTP/2 multiplexing, binary protobuf vs text JSON, no
per-request schema reparse). Tool is **k6** (not autocannon/ghz).

FR11: **Both transports operate simultaneously; nothing removed.** REST (HTTP/1.1+JSON) and gRPC
(HTTP/2+protobuf) both run; the flag chooses the caller's path; the REST endpoint is **not** deleted when
gRPC lands; the async `rabbit` path remains the default fallback.

FR12: **Wire-format & HW9 protection.** The existing `proto/release_notifier.proto` and its `generated/`
tree are untouched; the HW9 `SendWelcomeEmail/v1` and `WelcomeEmailOutcome/v1` RabbitMQ contracts, the
saga state machine, the reply queue and the timeout sweeper are unchanged; at the default (`rabbit`) the
HW9 saga and all existing HW7/HW9 tests and Behat scenarios stay green.

### NonFunctional Requirements

NFR1: **Default-safe, opt-in migration.** `WELCOME_EMAIL_TRANSPORT` defaults to `rabbit`; `rest`/`grpc`
are opt-in. The HW9 saga + tests + wire contracts remain 100% intact by default; the REST/gRPC paths
cannot regress production unless explicitly enabled.

NFR2: **Caller-waits semantics on the sync paths (documented trade-off).** On `rest`/`grpc` the caller
**blocks** for `sent|failed`, removing the broker buffer and the sweeper's never-hangs guarantee on those
paths; the sync client enforces its **own deadline + bounded retry/backoff** (arch §7.4: deadline 10s,
3 attempts, 200/500/1000ms backoff, retry on `UNAVAILABLE`/`DEADLINE_EXCEEDED`). The `rabbit` default
retains the sweeper.

NFR3: **Transport interchangeability over a single seam.** All three transports satisfy the same
`WelcomeEmailRelay`-shaped seam and are interchangeable by flag with no change to the saga orchestration;
the server runs the **same** `SendWelcomeEmailHandler` for all three.

NFR4: **Generated code isolation.** buf output lives in a dedicated `gen/` dir separate from the committed
`generated/`, with its own PSR-4 prefixes (`Notification\Welcome\V1\`, `GPBMetadata\Proto\Notification\`);
the legacy `make proto` flow and the committed `generated/` are unaffected.

NFR5: **Quality gates & CI.** Monolith `composer lint` + `phpunit --testsuite Unit` + `composer psalm`
(100%); the notification service's own gates. The **deptrac baseline must not grow** (stays `{}`) on both
deployables: new edges reuse existing Infrastructure layers. A new gate (`make buf-lint` + the new tests)
is added and a `grpc.yml` workflow + one new `.github/required-pr-checks.txt` row is registered;
`gen/` is excluded from hand-written gates exactly as `generated/` is.

NFR6: **Local dev / runtime.** `docker compose up` brings up both services with the new gRPC server
process for Service B (plaintext, on `:9002`, mirroring `bin/grpc.php` / `.rr.grpc.yaml`); flipping the
flag demonstrates the welcome path over `rabbit`/`rest`/`grpc`. The PHP gRPC **client** runs in the
**root/monolith image only** (`ext-grpc` confined there); Service B stays runtime-pure on RoadRunner.
**Booting the stack and running the k6 benchmark is confirmed with the user separately** before execution.

NFR7: **Independent deployability preserved.** No shared database; the sync paths add one new synchronous
coupling (A→B) **only when enabled**; each service still builds, migrates and runs against its own
Postgres. The default (`rabbit`) preserves the fully-decoupled HW9 topology.

NFR8: **Observability (reserved).** The sync paths may emit per-transport request/outcome counters and
latency; this reuses the existing metrics plane and is not a blocking deliverable of this assignment
(exact counters are deferred). No story is gated on it.

### Additional Requirements

_(Architecture-derived technical requirements that shape implementation — D1–D8, arch §2–§13.)_

- **AR-TOOL1 — Image installs, by image (arch §2/§10).** Root `Dockerfile` (monolith) adds `ext-grpc`
  (+ optional `ext-protobuf`) via `install-php-extensions grpc protobuf` and **`grpc/grpc` in
  `composer.json`** (provides `\Grpc\BaseStub`/`ChannelCredentials`/`UnaryCall` for runtime + psalm symbol
  resolution, RD7), plus `buf` (pinned) (codegen runs in this container). `apps/notification/Dockerfile`
  adds `spiral/roadrunner-grpc` + `google/protobuf` (composer), the `rr` binary, and (via the **root** build
  context, RD3) `COPY apps/notification/{…} …` + `COPY proto ./proto` + `COPY gen ./gen`. The
  **load-bearing asymmetry:** Service B needs **no `ext-grpc`** (RoadRunner's Go process terminates gRPC
  and the Spiral plugin emits a pure-PHP server interface); only Service A's saga-worker needs the PHP
  gRPC runtime, so `ext-grpc` + `grpc/grpc` are in the **root image only** (D1/R3/RD7 resolution).
- **AR-BUF1 — buf v2, three plugins, isolated `gen/` (D2/NFR4, RD2).** `buf.gen.yaml` runs three plugins
  off the one new proto, all → `out: gen`: (1) messages = **remote `buf.build/protocolbuffers/php`**;
  (2) Service B **server** interface = **local vendored Spiral**
  `tools/bin/protoc-gen-php-grpc-2025.1.12-linux-amd64/protoc-gen-php-grpc`; (3) Service A **client** stub =
  **remote `buf.build/grpc/php`**. `buf lint` is fully offline (the hard AC); `buf generate` needs network
  for the two remote plugins (acceptable codegen-time dependency) — **offline fallback** = a pinned
  `grpc_php_plugin` binary + a `protoc-gen-php` shim wrapping `protoc --php_out`. **Pin** buf + plugin
  versions. `make proto` and `generated/` are untouched (N7).
- **AR-PROTO1 — New proto, frozen legacy (D3/N2/FR12, RD1).** `proto/notification/welcome/v1/welcome.proto`
  (file path matches the package dir for buf `PACKAGE_DIRECTORY_MATCH`), package `notification.welcome.v1`,
  request fields mirror the HW9 `SendWelcomeEmail/v1` payload (`saga_id`, `int64 subscription_id`, `email`,
  `repository`) so the handler input is identical (FR5). `buf.yaml` **ignores `proto/release_notifier.proto`
  from lint** (it predates buf STANDARD; frozen by N2). Generated layout:
  `gen/Notification/Welcome/V1/{SendWelcomeEmailRequest,SendWelcomeEmailResponse,Outcome,
  WelcomeEmailServiceInterface,WelcomeEmailServiceClient}.php` + `gen/GPBMetadata/Proto/Notification/`.
- **AR-SVRB1 — Service B surfaces over the unchanged handler (D4/D7/N3/FR5, RD6/RD9).** The NEW
  Service B **transport adapters** — `App\Sending\Infrastructure\Grpc\WelcomeEmailGrpcService implements
  WelcomeEmailServiceInterface` (`final readonly`, `#[\Override]`, modeled on
  `src/Grpc/ReleaseNotifierService.php`) and `App\Sending\Infrastructure\Http\WelcomeEmailController`
  (`POST /internal/welcome-emails`, registered in `apps/notification/http/index.php` beside `/health`,
  `/metrics`) — both wrap the **same** `App\Sending\Application\SendWelcomeEmailHandler` (which is `void`
  and throws) and a new `WelcomeEmailFactory` (builds the `WelcomeEmail` VO from request → VO construction
  *is* validation). Outcome mapping is in the **adapter, not the handler**, with this **exact catch order**
  (load-bearing: `WelcomeAlreadyFailedException` and `WelcomeInFlightException` both extend
  `\RuntimeException`): (1) normal return → `OUTCOME_SENT`; (2) `WelcomeAlreadyFailedException` →
  `OUTCOME_FAILED` (a normal OK response that drives saga compensate); (3) `WelcomeInFlightException` →
  gRPC **ABORTED** / REST **409** (benign contention — caller leaves saga pending, retries next tick, does
  NOT drive saga); (4) `ValidationException`/`InvalidArgumentException` → **INVALID_ARGUMENT** / 400;
  (5) any other `\Throwable` (rethrown send failure) → **INTERNAL** / 500 (transient). The handler still
  publishes its AMQP reply as a harmless, idempotent side effect (arch §6.1/§13).
- **AR-STAT1 — One `App\Sending\Infrastructure\Error\ExceptionStatusMap` per side (D7/FR6/R6, RD6).** Add
  `toGrpcStatus(\Throwable): int` (returning Spiral `StatusCode::*`) and a symmetric `toHttpStatus()`, both
  with a `400`/`INVALID_ARGUMENT` arm for the new `WelcomeRequestValidationException` **and** a
  `409`/`ABORTED` arm for `WelcomeInFlightException` (load-bearing, RD6 — without it InFlight extends
  `\RuntimeException` → maps to UNAVAILABLE → the client retries lock contention). The gRPC server's
  `mapException()` mirrors `ReleaseNotifierService::mapException()` (INTERNAL → `ServiceException`, else
  `GRPCException`). The same map's `toHttpStatus()` drives the REST status. The `401/403` (auth) rows are
  **reserved** mappings (v1 has no auth — arch §6.3/§13).
- **AR-SEAM1 — Sibling outcome-returning port (D5/FR7/DC1, RD9).** New Saga.Domain port
  `SyncWelcomeEmailSender::send(SendWelcomeEmail): WelcomeOutcome` returns the **caller-side existing**
  `App\Saga\Enrollment\Application\HandleOutcome\WelcomeOutcome` enum (the one the
  `HandleWelcomeEmailOutcomeCommand` carries — distinct from the server-side
  `App\Sending\Domain\WelcomeOutcome` the handler publishes; the wire enum `Notification\Welcome\V1\Outcome`
  maps to each at its boundary); the async `WelcomeEmailRelay::publish(): void` port is **untouched**. The
  sync relays drive the saga by dispatching the **existing** `HandleWelcomeEmailOutcomeCommand` through the
  in-house `CommandBus` (reusing `HandleWelcomeEmailOutcomeHandler` verbatim — no new saga logic). A thin
  Saga.Application use-case `RelayPendingWelcomeEmailsSync` wraps the sender + command bus; on transport
  exhaustion it throws `SyncWelcomeSendException` and leaves the saga unadvanced for the next worker tick.
- **AR-RETRY1 — Deadline + retry policy replaces broker buffer + sweeper (arch §7.4/NFR2/R5).** Single
  source of truth in `config/settings.php` under a `welcome_sync` block (env-overridable):
  `WELCOME_EMAIL_SYNC_DEADLINE_SECONDS=10`, `WELCOME_EMAIL_SYNC_MAX_ATTEMPTS=3`,
  `WELCOME_EMAIL_SYNC_BACKOFF_MS=200,500,1000`. Retry on transport `UNAVAILABLE` (14) /
  `DEADLINE_EXCEEDED` (4) (REST: connect error / 502 / 503 / 504); **no retry** on `INVALID_ARGUMENT` (3),
  `INTERNAL` (13), or a clean `FAILED` business outcome (terminal → compensate the saga). Retries are safe:
  the welcome ledger's `UNIQUE(subscription_id)` claim makes a re-sent request a no-op (`AlreadySent` →
  still replies `sent`).
- **AR-FLAG1 — Flag-driven DI selection, default `rabbit` (D5 §7.5/FR8/NFR1, RD4).** `config/settings.php`
  adds `welcome_email.transport`; `config/container.php` binds the **ports** (`WelcomeEmailRelay`,
  `SyncWelcomeEmailSender`) and a factory picks the concrete by the flag (`grpc`→`GrpcWelcomeEmailRelay`,
  `rest`→`RestWelcomeEmailRelay`, default → the existing async relay; the sync sender is never resolved on
  `rabbit`). **`SagaWorker` itself does NOT change** (RD4): `tick()`→`relay->relay()` and the AMQP reply-loop
  are transport-agnostic; the migration swaps only the **relay/use-case binding** in DI. The AMQP reply
  consumer + sweeper keep running on **all** transports and `saga-worker` keeps `depends_on: rabbitmq`; only
  the **send** call (relay→notification) migrates from AMQP-publish to gRPC/REST. On sync paths no
  `SendWelcomeEmail` is published; the handler's async outcome reply is consumed by the running reply
  consumer as a no-op (RD5).
- **AR-DEPLOY1 — Service B gRPC = a second supervised process in the notification container (D6/NFR6,
  RD3).** `apps/notification/bin/grpc.php` (verbatim shape-copy of `bin/grpc.php`) + `.rr.grpc.yaml`
  (`listen: tcp://0.0.0.0:9002`, `proto: proto/notification/welcome/v1/welcome.proto`). `bin/start.sh` forks
  `rr serve -c .rr.grpc.yaml &` on `:9002` (plaintext) alongside the existing `php -S :8081` and
  `exec bin/consumer.php`. The `notification-svc` image **build context becomes the repo root (`context: .`)
  with `dockerfile: apps/notification/Dockerfile`** so the Dockerfile can `COPY apps/notification/{…}` +
  `COPY proto ./proto` + `COPY gen ./gen`; `.dockerignore` is updated to keep the root context lean.
  `docker-compose.yml` publishes `:9002` from `notification-svc` and the `saga-worker` service gets
  `WELCOME_EMAIL_TRANSPORT` + `WELCOME_EMAIL_REST_ENDPOINT` + `WELCOME_EMAIL_GRPC_TARGET` and keeps
  `depends_on: rabbitmq` (RD4). No separate `notification-grpc` compose service. No TLS/health-probe (N6).
- **AR-GATE1 — New gates, both baselines `{}` (D8/NFR5/R7/R8).** `make buf-lint` (offline) + the new
  gRPC/REST tests fold into the existing `make test` / notification unit suites; a new **`grpc.yml`**
  workflow (`name: gRPC contract (buf lint)`) and **one** new `.github/required-pr-checks.txt` row. deptrac:
  `Saga.Infrastructure` gains the two client adapters; `Notification.Infrastructure` gains the gRPC server
  + REST controller + factory — both already-allowed Infrastructure→{Application,Domain,Shared} edges, no
  new layer. The generated `gen/` tree is outside `paths:` (unscanned by deptrac, like `generated/`) and
  excluded from phpcs. For **psalm** (root `psalm.xml`): add `<directory name="gen"/>` to `projectFiles`
  **with** `<ignoreFiles><directory name="gen"/></ignoreFiles>` so generated symbols resolve at errorLevel 1
  but the generated code is not analyzed (RD7; arch §9 corrected — it previously claimed "no psalm change").
- **AR-DOCS — Architecture docs sync (AC11, RD10f).** `architecture.md` (authored) + ADR
  `docs/adr/0004-rest-to-grpc-welcome-email.md` (continuing the `0001`–`0003` series) + the LikeC4 model
  in `docs/architecture/` (via `likec4-architecture-sync`) document the new proto/package + buf wiring, the
  gen dir, the Service B gRPC server + REST endpoint, the Service A client adapters + flag, the status
  mapping, the client-runtime decision, and the deadline/retry policy. ADR-0004 additionally records the
  **introduced-REST-baseline** rationale (user-confirmed — no pre-existing sync REST call), the
  reachable-vs-reserved status codes, and the unsupervised forked `rr` risk under `set -e` (watchdog
  optional, or accepted).

## Epic List

### Epic 1: Contract & buf codegen toolchain (greenfield)
Stand up the gRPC contract and the buf codegen toolchain with **zero application code**. Add the new
`proto/notification/welcome/v1/welcome.proto` (legacy `proto/release_notifier.proto` frozen); add `buf.yaml` +
`buf.gen.yaml` with the three plugins (remote `buf.build/protocolbuffers/php` messages, local vendored
Spiral server interface, remote `buf.build/grpc/php` client stub) emitting into an isolated `gen/` and register the new PSR-4
prefixes in **both** composer.json files; install the codegen + runtime tooling in both Docker images
(`ext-grpc` + `grpc/grpc` + `buf` in the root image; `spiral/roadrunner-grpc`/`google/protobuf`/`rr` in
`apps/notification`); add `make buf-lint`/`make buf-generate`. **Story 1.3 is a P0 "prove-in-image" gate**
that actually runs `make buf-lint` (offline) + `make buf-generate` and verifies all three generated outputs
(messages, Spiral server interface, client stub) land in `gen/` before any app code depends on them, then
commits the stubs. After this epic the contract + stubs exist and are gate-green; no transport behaves yet.
(Phases P0–P1)
**ACs covered:** AC1, AC2 ; supports AC3–AC11 downstream. FR1, FR2, FR12 (legacy frozen). NFR4.

### Epic 2: Service B transport surfaces over the unchanged handler
Add the two **net-new transport adapters** on Service B (notification) over the **unchanged**
`SendWelcomeEmailHandler`. First the error-mapping arm (`toGrpcStatus()` + symmetric `toHttpStatus()` 400)
